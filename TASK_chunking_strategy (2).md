## Context You Must Understand First

### Why this document is hard
The RBI KYC Master Direction is a 100+ page regulatory document with these specific problems:
- Heavily cross-referenced: "as referred to in clause 16(b) above" — chunks lose this context
- Amendment layers: paragraphs begin with "Substituted vide..." making them noisy
- Dangling pronouns: "They shall also ensure..." — who is "they" depends on prior paragraph
- Nested clause hierarchy: Part I → Chapter II → Section 16 → Sub-clause (b)(iii)
- Mix of tables, schedules, annexures, and narrative prose — all in one file

Standard fixed-size or sentence chunking produces retrieval noise because chunks inherit broken context from the above.

### Why Agentic Chunking is the primary strategy for this document

After evaluating both strategies against the RBI KYC document's specific pathologies, **agentic chunking is the recommended primary strategy** for this use case. Reasons:

- RBI KYC queries from fintech developers and compliance officers are **exploratory and open-ended** — not always predictable in advance
- The document has **deep cross-references and pronoun chains** that only LLM-based resolution can fix reliably
- Agentic chunks give the RAG chain **raw coverage** of the entire document, including edge cases and exceptions that a Q&A library might miss
- Proposition extraction handles **novel queries** — things a compliance officer asks that weren't anticipated when the Q&A library was generated

The Q&A library (Strategy B) remains implemented for **comparison and benchmarking** via `eval_chunking.py`. It may outperform on predictable, high-frequency queries. The eval harness will determine the final call.

## Strategy A: Agentic Chunking (Proposition Extraction)

### What it does
Uses an LLM to transform noisy regulatory paragraphs into standalone, self-contained propositions before chunking. Each proposition can be understood without reading the surrounding text.

### Example transformation
**Input paragraph (raw from RBI doc):**
> "They shall also ensure, in terms of sub-rule (14) of Rule 9, that the records and documents are preserved for a period of five years after the business relationship ends or the transaction is completed, whichever is later."

**Output propositions:**
```
- Regulated entities must preserve KYC records for five years after the business relationship ends. (Rule 9(14))
- Regulated entities must preserve KYC records for five years after the transaction is completed. (Rule 9(14))
- The five-year retention period applies from whichever event occurs later — end of business relationship or completion of transaction. (Rule 9(14))
```

### Implementation steps

**Step 1: Pre-process paragraphs**
- Use `pdfplumber` output (already loaded via `loader.py`) — do not reload the PDF
- Split into raw paragraphs using double-newline boundaries
- Filter out: page numbers, headers/footers (lines < 40 chars that repeat), amendment notices ("Substituted vide RBI circular..."), blank lines
- Preserve: the section/chapter heading context for each paragraph (carry it as metadata)

**Step 2: Proposition extraction via Groq**
- Batch paragraphs: process in batches of 3 paragraphs per API call for Llama 8B (quality degrades on larger batches)
- Use the `build_prompt()` function defined in the section below — do NOT inline prompts
- Parse JSON response; on parse failure, fall back to sentence splitting for that batch (do not crash)
- Log failed batches with paragraph index for debugging
- Set `temperature=0.0` for all Groq calls — deterministic output reduces hallucination on citations

**Step 3: Create TextNodes**
- Each proposition becomes one `TextNode`
- Metadata to attach to every node:
  ```python
  {
      "source": "rbi_kyc_master_direction",
      "strategy": "agentic",
      "section": "<extracted section heading>",
      "original_paragraph_idx": <int>,
      "proposition_idx": <int within paragraph>,
      "char_count": <int>
  }
  ```

**Step 4: Deduplication**
- After extraction, deduplicate propositions using cosine similarity > 0.92 (use BGE embeddings, same model already in pipeline)
- Keep the longer/more specific proposition when deduplicating

## Prompt Engineering — Agentic Chunking

### Why the prompt is load-bearing

The proposition extraction prompt must handle **6 distinct pathologies** of RBI regulatory text simultaneously:
1. Dangling pronouns — "they/them/their" with no local referent
2. Cross-references — "as referred to in clause 16(b) above"
3. Compound obligations — multiple SHALL/MUST in one sentence
4. Amendment noise — "Substituted vide RBI circular dated..."
5. Modal verb precision — SHALL vs MAY vs SHOULD have different legal weight
6. Numerical threshold precision — exact INR amounts and time periods must not be paraphrased

A generic "extract facts" prompt handles maybe 2 of these. All 6 must be addressed explicitly.

### Prompt architecture

Every prompt is structured in 4 layers:
```
Layer 1 — Role / Persona
Layer 2 — Task Definition  
Layer 3 — Explicit Rules (numbered, unambiguous, with DO NOT counterparts)
Layer 4 — Output Format + Correct Example + Wrong Example
```

The wrong example in Layer 4 is not decoration — it anchors the model against its most common failure modes (pronoun retention, citation dropping) after 30+ batches.

### System prompt — Llama 3.1 8B via Groq (primary, your stack)

### `build_prompt()` function — use this in `chunker.py`

This is the single function that selects the correct system prompt based on the model
configured in `.env` and constructs the user message per batch.

```python
# ingestion/chunker.py

from config.settings import settings

# --- System prompts (defined above, pasted in full) ---
PROPOSITION_SYSTEM_PROMPT_LLAMA = """..."""   # paste Llama prompt here
PROPOSITION_SYSTEM_PROMPT_CLAUDE = """..."""  # paste Claude prompt here

# Map model prefixes to their prompt
_PROMPT_REGISTRY = {
    "groq/llama":    PROPOSITION_SYSTEM_PROMPT_LLAMA,
    "groq/mixtral":  PROPOSITION_SYSTEM_PROMPT_LLAMA,   # same structure works
    "claude":        PROPOSITION_SYSTEM_PROMPT_CLAUDE,
}

def _select_system_prompt(model: str) -> str:
    """
    Select the correct system prompt based on the model string from .env.
    Falls back to Llama prompt if model is unrecognised — safe default.
    """
    model_lower = model.lower()
    for prefix, prompt in _PROMPT_REGISTRY.items():
        if model_lower.startswith(prefix):
            return prompt
    # Unknown model — use Llama prompt as safe fallback, log a warning
    import logging
    logging.warning(
        f"Unrecognised model '{model}' — falling back to Llama system prompt. "
        f"Add it to _PROMPT_REGISTRY in chunker.py if needed."
    )
    return PROPOSITION_SYSTEM_PROMPT_LLAMA


def build_prompt(
    paragraphs: list[str],
    section_heading: str,
    model: str | None = None,
) -> tuple[str, str]:
    """
    Build the system prompt and user message for a batch of paragraphs.

    Args:
        paragraphs:      List of raw paragraph strings from pdfplumber (max 3 for
                         Llama 8B, up to 8 for Claude/GPT-4o).
        section_heading: e.g. "Chapter II — Section 16: Customer Due Diligence"
                         Passed in user message so system prompt stays cacheable.
        model:           Model string from .env (e.g. "groq/llama-3.1-8b-instant").
                         Defaults to settings.AGENTIC_PROPOSITION_MODEL if not passed.

    Returns:
        Tuple of (system_prompt: str, user_message: str)

    Usage:
        system_prompt, user_message = build_prompt(batch, section_heading)
        response = groq_client.chat.completions.create(
            model=settings.AGENTIC_PROPOSITION_MODEL,
            temperature=0.0,
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user",   "content": user_message},
            ]
        )
    """
    if model is None:
        model = settings.AGENTIC_PROPOSITION_MODEL

    system_prompt = _select_system_prompt(model)

    # Separate paragraphs clearly so the model knows where each ends
    para_block = "\n\n---\n\n".join(
        f"[Paragraph {i + 1}]\n{p.strip()}"
        for i, p in enumerate(paragraphs)
    )

    user_message = (
        f"Section context: {section_heading}\n\n"
        f"Process these {len(paragraphs)} paragraph(s) and return a single "
        f"JSON array containing all propositions from all paragraphs combined.\n\n"
        f"{para_block}"
    )

    return system_prompt, user_message
```

| Model | Batch size | Temperature | Notes |
|---|---|---|---|

| `gpt-4o` | 8 paragraphs | 0.1 | Markdown headers, "do not" rules effective |

## Strategy B: Pre-Generated Q&A Library

### What it does
Generates a curated set of question-answer pairs from the document **offline** (one-time batch job). At query time, the user's question is matched against stored questions, and the stored answer is returned — not the raw document chunk.

This means retrieval quality is decoupled from document noise. The Q&A pairs are the clean knowledge layer.

### When to use Q&A library vs Agentic Chunking

| | Agentic Chunking | Q&A Library |
|---|---|---|
| **Best for** | Open-ended, exploratory compliance queries | Predictable, high-frequency known questions |
| **Handles novel queries** | Yes | No — returns nearest stored question |
| **Answer consistency** | Variable (RAG synthesis) | High (pre-written) |
| **Source text access** | Yes (proposition + metadata) | No (pre-written answer only) |
| **Maintenance on doc change** | Re-ingest | Regenerate + review all pairs |
| **LLM at query time** | Yes (synthesis) | No (pure vector similarity) |

For RBI KYC, agentic chunking is primary. Q&A library is retained for benchmarking.

### Implementation steps

**Step 1: Q&A generation script (offline, run once)**
Create `scripts/generate_qa_library.py` — this is a standalone script, NOT part of the live pipeline.

```python
# scripts/generate_qa_library.py
# Usage: python scripts/generate_qa_library.py --input data/rbi_kyc_master.pdf --output data/qa_library.json
```

- Load PDF via existing `loader.py`
- Split into sections using heading detection (lines matching `r'^(PART|CHAPTER|SECTION|\d+\.)' `)
- For each section, call Groq using the `build_qa_prompt()` function defined below
- Merge all Q&A pairs into `data/qa_library.json`
- Add a metadata header:
  ```json
  {
    "generated_at": "<ISO timestamp>",
    "source_document": "rbi_kyc_master_direction",
    "model_used": "groq/llama-3.1-8b-instant",
    "total_pairs": "<int>",
    "qa_pairs": []
  }
  ```

**Step 2: Ingestion into Qdrant**
Create `ingestion/qa_ingester.py`:
- Load `data/qa_library.json`
- Create one `TextNode` per Q&A pair
- **Embed the question text** (not the answer) for retrieval — this matches user query semantics
- Store answer + section as metadata
- Metadata per node:
  ```python
  {
      "source": "rbi_kyc_master_direction",
      "strategy": "qa_library",
      "section": "<section name>",
      "question": "<the question text>",
      "answer": "<the full answer>",
      "char_count": <int>
  }
  ```

**Step 3: At query time**
- User query → embed → find most similar question(s) → return stored answer(s)
- The LLM synthesises from the stored answers, not the raw document
- This is handled in `retriever.py` — the strategy selection logic must pass the correct Qdrant collection name so the retriever reads the right index

## Prompt Engineering — Q&A Library Generation

### What the Q&A generation prompt must accomplish

Unlike agentic chunking (which processes paragraphs), Q&A generation works at **section level** and must produce questions that real compliance officers and fintech developers would actually ask. The failure mode is generating obvious, surface-level questions ("What is KYC?") instead of actionable, specific ones ("What documents are acceptable for address proof for a non-resident individual?").

The prompt must force coverage across 5 question types:
1. **Obligation questions** — what must regulated entities do?
2. **Threshold questions** — what are the monetary/time limits?
3. **Exception questions** — when does a rule not apply?
4. **Definition questions** — who qualifies as X?
5. **Process questions** — what is the step-by-step procedure for Y?

```python
            temperature=0.1,   # slight creativity acceptable for question variety
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user",   "content": user_message},
            ]
        )
    """
    if model is None:
        model = settings.QA_GENERATION_MODEL
    if n_pairs is None:
        n_pairs = settings.QA_PAIRS_PER_SECTION

    # Inject n_pairs into the system prompt for Llama
    # (Claude prompt handles it via user message — see below)
    system_prompt = _select_qa_system_prompt(model)
    system_prompt = system_prompt.replace("{n_pairs}", str(n_pairs))

    user_message = (
        f"Section heading: {section_heading}\n\n"
        f"Generate {n_pairs} Q&A pairs from the following section text.\n"
        f"Ensure coverage of obligation, threshold, exception, definition, "
        f"and process question types.\n\n"
        f"--- SECTION TEXT START ---\n"
        f"{section_text.strip()}\n"
        f"--- SECTION TEXT END ---"
    )

    return system_prompt, user_message
```

### Temperature and batch guidance for Q&A generation

| Model | Temperature | Pairs per section | Notes |
|---|---|---|---|
| `groq/llama-3.1-8b-instant` | 0.1 | 5–8 | Higher pairs → quality drops; keep ≤ 8 |
| `groq/llama-3.1-70b-versatile` | 0.1 | 8–10 | Better edge case and exception coverage |
| `claude-sonnet-3-7` | 0.2 | 8–12 | Generates nuanced exception/penalty questions naturally |

Set `QA_PAIRS_PER_SECTION=8` in `.env` as default. This is passed into `build_qa_prompt()`.

## Layered Retrieval Architecture

### Why layer both strategies

The two strategies have **complementary failure modes** — their weaknesses don't overlap:

| Query type | Agentic chunking | Q&A library |
|---|---|---|
| High-frequency known questions ("V-CIP timeline?") | Returns 3 partial propositions needing synthesis | Returns one complete pre-written answer |
| Novel / edge case queries ("Does rule X apply to OCI cardholders?") | Has full document coverage — handles it | Returns wrong nearest Q&A match |
| Cross-reference heavy queries | Resolves pronouns and refs — handles it | Pre-written answer may have missed the nuance |
| Open-ended exploratory queries | Good | Poor |

Layering them means the system gets complete answers on known questions **and** full coverage on unknown ones. Neither strategy alone achieves both.

### Three layering patterns — implemented in `cascading_retriever.py`

#### Pattern 1 — Cascading (recommended for Phase 2, implement first)

Query Q&A library first. If confidence is high enough, return its answer. If not, fall through to agentic chunks.

```
User query
    ↓
Q&A library retrieval  (rbi_kyc_qa_library)
    ↓
top-1 similarity score ≥ CASCADE_CONFIDENCE_THRESHOLD (default 0.85)?
    ├── YES → return Q&A answer directly  (fast path)
    └── NO  → agentic retrieval           (fallback path)
                  ↓
             rbi_kyc_agentic
                  ↓
             RAG chain synthesises from propositions
```

```python
# retrieval/cascading_retriever.py

from llama_index.core.schema import NodeWithScore
from config.settings import settings
import logging

logger = logging.getLogger(__name__)


class CascadingRetriever:
    """
    Queries the Q&A library first. If the top result exceeds the confidence
    threshold, returns it directly. Otherwise falls through to agentic chunk
    retrieval. Controlled by CASCADE_CONFIDENCE_THRESHOLD in .env.
    """

    def __init__(self, qa_retriever, agentic_retriever, threshold: float = 0.85):
        self.qa_retriever = qa_retriever
        self.agentic_retriever = agentic_retriever
        self.threshold = threshold

    def retrieve(self, query: str) -> list[NodeWithScore]:
        qa_results = self.qa_retriever.retrieve(query)

        if qa_results and qa_results[0].score >= self.threshold:
            logger.info(
                f"[cascading] Q&A hit — score={qa_results[0].score:.3f} "
                f"≥ threshold={self.threshold} — returning Q&A answer"
            )
            return qa_results

        logger.info(
            f"[cascading] Q&A miss — score={qa_results[0].score if qa_results else 'n/a':.3f} "
            f"< threshold={self.threshold} — falling through to agentic"
        )
        return self.agentic_retriever.retrieve(query)
```

#### Pattern 2 — Reciprocal Rank Fusion (Phase 2 upgrade, implement after cascading)

Query **both** collections simultaneously. Merge results using RRF. The RAG chain synthesises from the combined top-K — getting both a complete Q&A answer and supporting raw propositions in context.

```
User query
    ├──→ Q&A library retrieval  (top-5) ─┐
    │                                     ├── RRF merge → top-5 combined → rag_chain.py
    └──→ Agentic retrieval       (top-5) ─┘
```

```python
class FusionRetriever:
    """
    Queries both collections simultaneously and merges results using
    Reciprocal Rank Fusion (RRF). Passes combined top-K to rag_chain.py
    so the LLM synthesises from both a pre-written answer and raw propositions.
    No ML required — RRF is a deterministic re-ranking formula.
    """

    def __init__(self, qa_retriever, agentic_retriever, top_k: int = 5, rrf_k: int = 60):
        self.qa_retriever = qa_retriever
        self.agentic_retriever = agentic_retriever
        self.top_k = top_k
        self.rrf_k = rrf_k

    def retrieve(self, query: str) -> list[NodeWithScore]:
        # Query both collections (can be parallelised with ThreadPoolExecutor)
        qa_results = self.qa_retriever.retrieve(query)
        agentic_results = self.agentic_retriever.retrieve(query)

        return self._reciprocal_rank_fusion([qa_results, agentic_results])

    def _reciprocal_rank_fusion(
        self, result_lists: list[list[NodeWithScore]]
    ) -> list[NodeWithScore]:
        """
        RRF formula: score(d) = Σ 1 / (k + rank(d))
        where k=60 (standard constant), rank is 0-indexed position in each list.
        Higher score = better combined rank.
        """
        rrf_scores: dict[str, float] = {}
        node_map: dict[str, NodeWithScore] = {}

        for results in result_lists:
            for rank, node_with_score in enumerate(results):
                node_id = node_with_score.node.node_id
                rrf_scores[node_id] = (
                    rrf_scores.get(node_id, 0.0) + 1.0 / (self.rrf_k + rank + 1)
                )
                # Keep the node object for reconstruction
                if node_id not in node_map:
                    node_map[node_id] = node_with_score

        # Sort by fused RRF score descending, return top_k
        sorted_ids = sorted(rrf_scores, key=lambda x: rrf_scores[x], reverse=True)
        fused = []
        for node_id in sorted_ids[: self.top_k]:
            node = node_map[node_id]
            node.score = rrf_scores[node_id]   # replace original score with RRF score
            fused.append(node)

        return fused
```

#### Pattern 3 — Role-Separated Retrieval (Phase 3, requires rag_chain.py change)

Assign each strategy a different **role** in the prompt rather than competing for the same retrieval slot.

```
Q&A library  → "answer candidate" passed to LLM as probable answer
Agentic chunks → "evidence" passed to LLM as raw regulatory grounding

RAG chain prompt:
  "Answer candidate: {qa_answer}
   Supporting regulatory propositions: {agentic_chunks}
   Synthesise a final answer that is complete AND grounded in the propositions.
   If the answer candidate contradicts the propositions, trust the propositions."
```

This is the highest quality pattern — the LLM explicitly cross-checks the Q&A answer against raw regulatory text before responding. Hallucination risk drops significantly. Requires a prompt change in `rag_chain.py` — defer to Phase 3.

### Choosing between patterns

```
Phase 2 now:    RETRIEVAL_MODE=cascading
                → simplest, no rag_chain.py changes, interpretable logs
                → implement and validate first

Phase 2 end:    RETRIEVAL_MODE=fusion
                → upgrade once cascading latency is measured
                → two parallel Qdrant calls, RRF merge, richer LLM context

Phase 3:        Role-separated retrieval
                → requires rag_chain.py prompt change
                → highest answer quality, best for production
```

## Error Handling Requirements

- **Groq API failures**: Retry up to 3 times with exponential backoff (2s, 4s, 8s). On final failure, log the batch index and skip — do not crash the entire ingestion.
- **JSON parse failures**: On failed JSON parse from proposition extraction, log the raw response and fall back to sentence splitting for that batch.
- **Missing Q&A library file**: If `CHUNKING_STRATEGY=qa_library` but `QA_LIBRARY_PATH` file does not exist, raise a clear error: `"Q&A library not found at {path}. Run scripts/generate_qa_library.py first."`
- **Qdrant collection already exists**: Add a `--force-recreate` flag to the ingestion script. Without it, skip re-ingestion and log a warning.

## Notes for Implementation

- The `build_prompt()` and `build_qa_prompt()` functions are the single source of truth for all prompt construction. Never inline a system prompt directly in a Groq API call — always go through these functions.
- Both functions return `(system_prompt, user_message)` tuples. This keeps the system prompt cacheable at the Groq layer and the per-batch context in the user message where it belongs.
- The wrong example in the Llama system prompt is load-bearing — do not remove it. After 30+ batches, models drift back to their default behaviour. The wrong example anchors them against pronoun retention and citation dropping.
- Proposition extraction will be slow on first run (~5–10 mins for full document). Add a progress bar using `tqdm`.
- The Q&A generation script will likely cost ~$0.50–$1.00 in Groq credits for the full document. Run it once, commit `qa_library.json` to the repo.
- Qdrant collections for each strategy must be **completely separate** — do not mix them. This is what makes layered retrieval clean — each collection is a pure representation of its strategy.
- Start with `RETRIEVAL_MODE=cascading` for Phase 2. It requires no changes to `rag_chain.py`, produces interpretable logs, and gives you the data to decide whether to upgrade to `fusion`.
- The "Served by" column in the eval table is the most important diagnostic. After running `eval_chunking.py`, group queries by which strategy served them in cascading mode — this tells you where each strategy's natural domain is.
- Phase 3 upgrade (role-separated retrieval) requires a prompt change in `rag_chain.py`. Do not attempt it until cascading and fusion modes are validated and producing good eval scores.
- The two Qdrant collections being separate means you can re-ingest one without touching the other. If the RBI document is amended, regenerate only the affected collection.
